CS258 Database Systems

1. Introduction to Database Management Systems

Introduction

  • A DBMS (Database Management System) is software that sits between applications and the raw data on disk

  • It provides functions like:

    1. storing data
    2. modelling data
    3. accessing data: query + update
    4. analysing data: complex queries
    5. securing data
    6. ensure/maintain data consistency
    7. optimise data accesses

  • A DBMS is implemented in the 3 Schema Architecture:

    1. External schema - what the user / application sees
    2. Conceptual schema - entity-relationship level
    3. Internal schema - physical storage

  • This provides data independence:

    • Physical data independence - change internal details without changing conceptual/external layers
    • Logical data independence - change conceptual schema without breaking applications

Types of Data

  • Data comes in three types:

    • Structured - tables
    • Semi-structured - XML, JSON
    • Unstructured - web pages, text documents etc.

  • Relational databases are designed for structured data

2. Relational Model

Introduction

  • Def. A relation is a table of values, having:

    • A set of rows, called tuples
    • Each column has an attribute

  • The schema (or description) of a relation is:

    • denoted by R(A_1, A_2, \cdots, A_n)
    • where R is the name
    • and A_1, \cdots, A_n are the attributes

  • Each attribute has a domain \text{dom}(A_i)

  • The state of a relation is the set of tuples currently in the relation

    • i.e. an instance
    • written r(R)

  • In the formal relational model, relations follow set semantics (no duplicate tuples), but SQL follows multiset semantics (allows duplicate tuples)

Keys

  • A superkey of relation R is a subset of attributes SK that uniquely identify tuples in R

    • i.e. if t_1 \ne t_2, then t_1[SK] \ne t_2[SK]

  • A candidate key is a minimal superkey, i.e. removing any attribute from candidate key K results in a set of attributes that aren’t a superkey

  • One of the candidate keys is chosen to be the primary key

Integrity Constraints

  • The relational model includes the idea that the DB must satisfy constraints

    • Key constriaint: key values must be unique
    • Entity integrity: primary key attributes cannot be NULL
    • Referential integrity: every foreign key value must match an existing referenced key (or be NULL, if allowed)

  • A foreign key is a set of attributes that references a primary key in another table

Functional Dependencies

  • A functional dependency X \to Y over schema R means for any valid instance r(R), whenever two tuples agree on all attributes in X, they must agree on all attributes in Y

  • i.e. values of t[Y] depend on t[X]

  • Formally, for all t_1, t_2 \in r(R),

    • if t_1[X] = t_2[X] then t_1[Y] = t_2[Y]

  • we say X functionally determines Y

  • Functional dependencies matter, because:

    • they imply what attributes should be keys
    • they drive normalisation decisions

Attribute Closure

  • Given a set of functional dependencies $$, the closure X^+ is the set of all attributes functionally determined by X

  • We can use closure to find a key

    • X is a superkey iff X^+ contains all attributes of R

  • Algorithm idea:

    1. start with X^+ = X
    2. repeatedly apply FDs: if A to B and A \subseteq X^+, then add B to X^+
    3. stop when nothing new can be added

3. Basics of SQL

3.1 SQL as a DDL

Data Definition Language

  • A data definition language is a declarative language used to define schemas,relations, constraints etc.

  • SQL is a data definition language, which provides these core commands:

    • CREATE SCHEMA - create a collection of relations
    • CREATE TABLE - define columns + types + constraints
    • ALTER TABLE - add/drop/modify columns/constraints
    • DROP TABLE - remove table definition (and data)

  • One example is:

CREATE TABLE orders (
  order_id   BIGINT PRIMARY KEY,
  user_id    BIGINT NOT NULL,
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  status     TEXT NOT NULL CHECK (status IN ('pending','paid','shipped')),
  total      NUMERIC(10,2) NOT NULL CHECK (total >= 0),

  UNIQUE (order_id), -- redundant here (PK already unique), shown just as syntax

  FOREIGN KEY (user_id) REFERENCES users(user_id)
    ON DELETE RESTRICT
    ON UPDATE CASCADE
);

Data Types

  • Each column must* have a data type
  • Common data types are:
    • INT
    • DECIMAL
    • CHAR(n) / VARCHAR(n)
    • TEXT
    • BOOLEAN
    • DATE / TIME / TIMESTAMP

Constraints

  • NOT NULL - declares a column to be not null
  • PRIMARY KEY (...) - declares a set of attributes to be a primary key
  • UNIQUE - declares a candidate key (can be NULL)
  • CHECK - check constraint
  • FOREIGN KEY - foreign key constraint, for example 
    FOREIGN KEY (courseID) REFERENCES courses(courseID) ON UPDATE CASCADE
  • DEFAULT - specify default value, for example 
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP`

3.2 SQL as a DML

Data Manipulation Language

  • A data manipulation language provides updates and queries.

  • SQL is a data manipulation language, providing core features like:

    • INSERT INTO ... VALUES - insert into a table
    • UPDATE ... SET ... WHERE ... - update a table
    • DELETE FROM ... WHERE ... - delete from a table

  • And queries in the form of SELECT statements, which have the form:

    SELECT ...
FROM ...
JOIN ...
WHERE ...
GROUP BY ...
HAVING ...
ORDER BY ...
LIMIT ...

3-Valued Logic

  • NULL has weird semantics due to 3-Valued Logic:

    • TRUE, FALSE, and UNKNOWN

  • To check if a column is NULL, use IS NULL or IS NOT NULL

    • note: =NULL will never evaluate to true

Name Aliasing

  • Aliasing of attributes can be done with AS, for example:

    SELECT s.studentID FROM students s

  • It is common to alias the table name, which is necessary for certain operations like self joins to specify which table it came from

String Patterns

  • LIKE and NOT LIKE can be used to compare strings to patterns
    • % = any string
    • _ = any character

Joins

  • In the relational model, data is split into multiple tables due to normalisation

    • Tables must be joined to query data across tables

  • The most basic type of join is the cross join, i.e. cartesian product

    • If |A| = m and |B| = n, then |A \times B| = m \times n
    • In simplest terms, is written as SELECT * FROM A, B
    • In modern SQL, this is written as SELECT * FROM A CROSS JOIN B

  • The natural join is an extension of the cross join, that joins in common attributes with identical data types and names

    • written as A NATURAL JOIN B

  • The theta join extends the natural join by providing a join condition

    • writen as R JOIN S ON <condition>

  • The INNER JOIN is the default type of theta join

    • rows from both R and S must exist to be joined

  • There are also outer joins, which preserve rows by substituting NULL for non-existent values

    • LEFT OUTER JOIN preserves data from left table, puts NULL for right table if not exists
    • RIGHT OUTER JOIN preserves data from right table
    • FULL OUTER JOIN is the default - pads both left and right

  • For theta joins, instead of usig ON to specify conditions, USING can be used for equi-joins:

    • Instead of SELECT * FROM students s INNER JOIN studentCourses c ON s.studnetID = c.studentID;
    • we can do SELECT * FROM studnets s INNER JOIN studentCourses c USING (studnetID);

3.3 Subqueries, Set Operations, Quantifiers

Subqueries

  • Queries itself can be used in the WHERE clause of another query

    • This is called a subquery

  • Subqueries can be:

    • Non-correlated - can run on its own
    • Correlated - depends on outer row (runs “per row” conceptually)

  • Two common operators used with subqueries are:

    • EXISTS(table) - returns true if the table is not empty
    • IN(table) - returns true if row is in the table

Set Operations and Quantifiers

  • ANY and ALL behave as existential and universal quantifiers:

    • x > ALL (subquery) means x is greater than every value returned
    • x > ANY (subquery) means x is gerater than at least one value returned

  • Set operations can be used to combine queries:

    • UNION - union of two tables
    • INTERSECT - intersection of two tables
    • EXCEPT (postgres) / MINUS (oracle) - set difference of two tables

  • Set operations by default use set semantics

    • appending ALL turns it into multiset semantics

  • The DISTINCT operator turns SQL’s default multiset semantics into set semantics

    • e.g. SELECT DISTINCT * FROM A returns all distinct rows from A

3.4 Aggregation and Window Functions

Aggregation Functions

  • An aggregation function is used to compute results based on multiple columns

  • Some common aggregation functions are:

    • COUNT(*) - number of rows
    • COUNT(col) - number of non-NULL values in col
    • SUM(col) - sum of a column
    • AVG(col) - avreage of a column
    • MIN(col) - minimum of a column
    • MAX(col) - maximum of a column

  • GROUP BY is used to group the aggregation by a set of columns

    • In the SELECT clause, attributes must be either aggregated, or part of the GROUP BY statement

  • To apply a filter on aggregated functions, use the HAVING clause

  • Core syntax:

    SELECT group_cols, AGG_FUNC(cols)
FROM ...
WHERE row_filter
GROUP BY group_cols`
HAVING group_filter
ORDER BY ...

Window Functions

  • Window functions compute values across related rows, but do not collapse the result like GROUP BY does

  • Core syntax:

    <window_function>(...) OVER (
    PARTITION BY ...
    ORDER BY ...
    [ROWS/RANGE frame ...]
)

  • PARTITION BY defines the groups to aggregate over

  • ORDER BY defines the order within each partition

  • For example, this query gets each employee + their department average salary

    SELECT e.emp_id, e.dept_id, e.salary,
       AVG(e.salary) OVER (PARTITION BY e.dept_id) AS dept_avg
FROM employee e;
Ranking Window Functions

  • Given a partition and an order:

    • ROW_NUMBER() retrieves the row number (no ties)
    • RANK() - ties share rank, and skips numbers after ties e.g. (1,1,3,…)
    • DENSE_RANK() - ties share rank, but there are no gaps e.g. (1,1,2,…)

  • For example to calculate the top 3 salaries per department:

    SELECT * FROM (
    SELECT e.*, ROW_NUMBER() OVER (
        PARTITION BY e.dept_id ORDER BY e.salary DESC
    ) AS rn
    FROM employee e
) t WHERE t.rn <= 3;
Running totals and moving calculations

  • We can use ROWS to specify a sliding window to perform the window function over

    • UNBOUNDED PRECEDING - no limit to the left
    • CURRENT ROW - the current row

  • For example, to get running total per user ordered by time:

    SUM(amount) OVER (
    PARTITION BY user_id 
    ORDER BY ts 
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
)

  • To get the moving average (e.g. last 7 rows)

    AVG(amount) OVER (
    PARTITION BY user_id 
    ORDER BY ts
    ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
) AS moving_avg_7
LAG/LEAD (differences between rows)

  • Used to refer to rows preceding and following the curent row

    • LEAD() gets the next row, LEAD(2) gets the row 2 in front
    • LAG() gets the previous row, LAG(2) gets the row 2 behidn

  • E.g. next event time:

    LEAD(ts) OVER (PARTITION BY user_id ORDER BY ts) AS next_ts

3.5 Common Functions

  • NULL handling

    • COALESCE(a,b,c): retrieves first non-NULL
    • NULLIF(a,b): NULL if a = b
    • CASE WHEN ... THEN ... ELSE ... END: case statement
    • IF(cond, x, y): MySQL-only shortcut for CASE
    • IFNULL(a,b): 2-arg COALESCE for MySQL only

  • String

    • LOWER(), UPPER()
    • LENGTH()
    • SUBSTRING()
    • REPLACE()
    • TRIM()
    • Concatenation: || in postgres, CONCAT() in MySQL

  • Numeric:

    • ABS(), ROUND(), CEIL(), FLOOR
    • POWER(a,b), SQRT()
    • MOD(a,b) / % in postgres
    • Random numbers: random() in postgres, RAND() in MySQL
    • GREATEST(a,b,...), LEAST(a,b,...)

  • Date/time

    • CURRENT_TIMESTAMP, CURRENT_DATE, CURRENT_TIME, NOW()
    • Extracting parts:
      • Postgres: EXTRACT(YEAR FROM ts)
      • MySQL: YEAR(ts), MONTH(ts), DAY(ts) etc.
    • Date arithmetic
      • Postgres: ts + INTERVAL '7 days'
      • MySQL: DATE_ADD(ts, INTERVAL 7 DAY), DATE_SUB(...)

  • Pattern Matching + Regex

    • LIKE
      • % is any number of characters
      • - is one single character
    • Regex:
      • Postgres: col ~ 'pattern'
      • MySQL: col REGEXP 'pattern'

  • Type casting

    • CAST(x AS type)
    • Postgres only: x::type

4. Advanced SQL

4.1 Views

Introduction to Views

  • A view is a named query that behaves like a table

    • It doesn’t usually store data, it behaves like a virtual table
    • Querying a view substitutes the view’s definition

  • For example:

    CREATE VIEW active_users AS
SELECT user_id, email
FROM users
WHERE is-active = true;

  • Views provide:

    • Abstraction / readability: hides complex joins
    • Security: expose only a certain set of columns / rows
    • Stability: keep a stable interface while underlying tables evolve

  • Some views can be updatable:

    • usually only if it maps cleanly to a single base table
    • postgres has rules for when a view is automatically updatable

Materialised Views

  • A materialised view stores the result of the query physically

    CREATE MATERIALIZED VIEW monthly_sales AS
SELECT date_trunc('month', paid_at) AS month,
       SUM(amount) AS total
FROM payments
WHERE status = 'paid'
GROUP BY 1;

  • The view must be refreshed to keep data updated:

    REFRESH MATERIALIZED VIEW monthly_sales;

  • Pros:

    • Fast reads (precomputed)
    • Great for reporting / analytics

  • Cons:

    • Can be stale
    • Refresh cost (and locking behaviour depends on DB)

  • View vs Materialized view:

    • View: mainly abstraction/security; performance depends on base query
    • Materialised view: performance boost by precomputing results

4.2 Assertions and Triggers

Assertions

  • An assertion is a global cosntraint that must always hold across the database
  • SQL standard supports: 
    CREATE ASSERTION name CHECK ( ... );
  • Most mainstain DBs (including PostgreSQL) do not implement general assertiosn
  • Other alternatives can be used to enforce rules, such as:
    • Foreign key / check constraints where possibel
    • Triggers
    • Transactions + locking
    • Application logic

Triggers

  • A trigger is code that runs automatically when an event happens on a table (or view)

    • Triggers are event-driven
    • they fire on events like INSERT, UPDATE, DELETE etc.

  • Trigger timing:

    • BEFORE triggers: run before the row is written
      • good for validation / modifying the row
    • AFTER triggers: run after the change
      • good for auditing / side effects
    • INSTEAD OF triggers: mainly for views

  • Trigger granularity:

    • Row-Level runs once per affected row (FOR EACH ROW)
    • Statement-level: runs once per statement

  • For example:

    CREATE OR REPLACE FUNCTION set_updated_at()
RETURNS trigger AS $$
BEGIN
    NEW.updated_at := now();
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_set_updated_at
BEFORE UPDATE ON users
FOR EACH ROW
EXECUTE FUNCTION set_updated_at();

  • Triggers can be dangerous as:

    • They hide side effects
    • Affect performance, e.g. row triggers on bulk updates are expensive
    • Concurrency issues: race conditions unless you lock correctly
    • Recursion: triggers triggering triggers

  • In PostgreSQL, there are constraint triggers:

    • used to enforce cross-row / cross-table constraints
    • created using CREATE CONSTRAINT TRIGGER ...
    • can be DEFERRABLE, INITALLY DEFERRED or INITIALLY IMMEDIATE

4.3 PSMs

  • A PSM (Persistent Stored Module) is code stored and executed inside the database server

    • Mainly uses procedures and functions

  • They use:

    • procedural constructs (variables, loops, IF/ELSE, exceptions)
    • can run multiple SQL statements in one call
    • can control transactions (in postgres, functions cannot COMMIT/ROLLBACK)

  • Procedures vs functions:

    • Function: returns a value/table; often used in SELECTs
    • Procedure: called for actions

  • Pros of PSMs

    • Performance - fewer client-server round trips, execute close to data
    • Security - grant permission to execute a procedure instead of direct table access
    • Consistency - enforce a workflow does all required inserts/updates safely
    • Reusability - shared logic across many apps/services

  • Cons of PSMs

    • Harder versioning/testing than app code
    • DB vendor lock-in (PL/pgSQL vs MySQL stored program syntax differs0
    • Debugging and observability can be worse than in application code
    • Logic split across app + DB can confuse ownership

  • PostgreSQL function:

    CREATE OR REPLACE FUNCTION top_customers(p_limit int)
RETURNS TABLE(user_id bigint, total_spend numeric)
LANGUAGE sql
AS $$
    -- insert query here ...
$$;

  • PostgreSQL procedure:

    CREATE OR REPLACE PROCEDURE transfer(p_from bigint, p_to bigint, p_amount numeric)
LANGUAGE plpgsql
AS $$
BEGIN
    -- insert code here ...
END;
$$;

  • MySQL function:

5. Normalisation

5.1 Introduction

Motivations

  • Guidelines for good relational database design:

    1. each tuple in a relation should represent one entity or relationship instance
    2. redundancy of tuples information is harmful and must be avoided
    3. NULL values within tuples is harmful and must be avoided
    4. design relations to avoid suprious tuples
      • spurious tuples are created by joining on an attribute that isn’t a key

  • Normalisation is a way of designing relational schemas to reduce redundancy and avoid anomalies:

    • Update anomaly: you must update the same fact in multiple places
    • Insert anomaly: you can’t insert one fact without another unrelated fact
    • Delete anomaly: deleting a row accidentally deletes a fact you still wanted to keep

  • Functional dependencies are the tool used to reason about redundancy

Laws of Functional Dependencies

  • The closure F^+ of a set of functional dependencies F is the set of all implied FDs from F

  • The implied FDs from F are derived using these rules:

    1. Reflexive: If Y \subseteq X, then X \to Y
    2. Augmentation: If X \to Y, then XZ \to YZ
      • notation: XZ := X \cup Z
    3. Transitive: If X \to Y and Y \to Z, then X \to Z
    4. Decomposition: If X \to YZ, then X \to Y and X \to Z
    5. Union: If X \to Y and X \to Z, then X \to YZ
    6. Pseudotransitivity: If X \to Y and WY \to Z, then WX \to Z

  • A non-trivial functional dependency is a FD X \to Y where Y is not a subset of X

Lossless Join and Dependency Preservation

  • When decomposing relations, we desire:
    • Lossless or non-additive decomposition
      • Joining decomposed tables should reconstruct the original data without spurious tuples
      • This is critical
    • Dependency preservation
      • Can enforce all original FDs by enforcing constraints on the decomposed tables without needing joins
      • This is sometimes not possible, but is desired
      • Otherwise checking updates for violation of FDs may require computing joins, which is expensive

5.2 Normal Forms

  • There are many normal forms of relational databases:

    • typically, 3NF (or BCNF) suffice
    • All normal forms up to BCNF depend on functional dependencies

  • Overview of NF definitions:

    • 1NF: all attributes are atomic and there is a key
      • “the key”
    • 2NF: non-key attributes must be dependent on the full key
      • “the whole key”
    • 3NF: non-key attributes must only depend on the key
      • “nothing but the key”
    • BCNF (Boyce-Codd Normal Form): if every determinant (of a non-trivial FD) is a superkey

1NF

  • Every attribute value is atomic and there is a key
    • i.e. no “multiple values in one cell”
  • This disallows:
    • Multi-valued attributes
    • Composite attributes
  • To move to 1NF, convert all multi-valued attributes into separate rows

2NF

  • Only relevant when you have a composite candidate key
  • A relation is in 2NF if:
    • it is in 1NF
    • and every nonkey attribute is fully functionally dependent on any key
    • So, if the key is (A, B), then a non-key attribute shouldn’t depend on just A or just B
  • 2NF improves data integrity by removing some storage anomalies
    • but there can still be anomalies regarding transitive functional dependencies

3NF

  • A relation is in 3NF if:
    • it is in 2NF
    • and there is no transitive functional dependency from a key to non-key attribute
  • More formally, for every non-trivial FD X \to A, at least one holds:
    1. X is a superkey, or
    2. A is a prime attribute (part of some candidate key)
  • It is always possible to find a dependency-preserving lossless-join decomposition that is in 3NF
  • 3NF removes redundancies that are in 2NF

BCNF

  • A relation is in BCNF if for every non-trivial FD X \to Y, X is a superkey

    • removes all FD-based redundancy

  • Most 3NF relations are in BCNF, but not all

    • BCNF is stricter than 3NF
    • Key difference from 3NF is that the RHS of a FD must not be a prime (key) attribute, unless the FD is trivial

  • For example:

    • {student, course} is a candidate key
    • fd1: {student, course} -> instructor
    • fd2: instructor -> course
    • This is NOT BCNF as instructor is not a superkey, and course is part of a key
    • This does NOT spoil 3NF as course is a key attribute, so we don’t have non-key -> non-key

  • Disadvantage of BCNF:

    • Dependency preservation is not guaranteed
    • Sometimes, 3NF may be used instead if dependency preservation is important

5.3 Denormalisation

  • Denormalisation means intentionally adding redundancy back into the scshema to improve performance or simplicity of queries

    • this is becuse joins are expensive

  • Common denormalisation techniques:

    • Storing derived values
    • duplicating attributes to avoid joins
    • precomputed summary tables / materialised views

  • Denormalisation is good when:

    1. read-heavy workloads + expensive joins
    2. reporting / analytics
    3. when data changes rarely
    4. can enforce consistency reliably

  • Denormalisaton is bad when:

    1. lots of writes/updates
    2. high correctness requirements
    3. when indexes alone solve the performance issue

6. Theory of Databases

6.1 Introduction

  • Relational algebra and relational calculus are both formal query languages for the relational model

    • Relational algebra is procedural: tells you how to get the result
    • Relational calculus is declarative: telsl you what the result should satisfy

  • By Codd’s theorem:

    • relational algebra and relational calculus are equivalent in their expressive power

  • SQL sits in between:

    • It is declarative in style
    • but the DBMS internally rewrites / optimises queries into someting close to relational algebra

6.2 Relational Algebra

  • Relational algebra takes relations as input and outputs 8relations* (closure property)

  • In the pure theory, relations are sets (no duplicates)

  • The core operators are:

    1. Selection: \sigma

      • Filter rows (like WHERE)
      • e.g. sigma_{dept='CS'}(Student)
      • is equivalent to:
      SELECT * FROM Student WHERE dept = 'CS';

    2. Projection: \pi

      • Pick columns from a relation
      • e.g. pi_{name}(Student)
      • is equivalent to:
      SELECT name FROM Student;

    3. Rename: \rho

      • Rename relation or attributes
      • similar to AS in SQL

    4. Cartesian product: \times

      • the same as FROM R CROSS JOIN S in SQL

    5. Set Operations: \cup, \cap, -

      • require same attributes/domains
      • the same as SQL UNION, INTERSECT, and EXCEPT

    6. Join: \bowtie

      • Join can be expressed as product + selection
      • Theta join: R \bowtie_{\theta} S = \sigma_\theta (R \times S)
        • For example in SQL:
        SELECT * FROM R JOIN S ON R.a = S.b;
      • Equijoin:
        • Theta join where condition is only equalities
      • Natural Join:
        • The default join operator in RA.
        • equivalent to SQL NATURAL JOIN

    7. Division (for all)

      • operator behind for all queries
      • let R(XY), S(Y) be relations
      • R(XY) \div S(Y) is a relation T(X) where X-tuples are paired with every Y-tuple in S
      • used for queries like “find students who are enrolled in all required modules”

6.3 Relational Calculus

  • Relational calculus is logic-based: you specify a condition that output tuples must satisfy

  • Two common forms:

    • Tuple Relational Calculus: uses notation like t.attribute
      • for example \{t | Student(t) \land t.dept = 'CS'\}
    • Domain Relational Calculus: uses variables for attribute values rather than whole tuples
      • for example\{\langle sid, name \rangle | \exists dept (Student(sid, name, dept) \land dept = 'CS')\}

  • Relational calculus uses quantifiers:

    • \exists: existential quantifier
    • \forall: universal quantifier

  • Relational calculus is based off first order logic

    • using predicates and propositions
    • roughly speaking, a predicate is a schema and a proposition is a tuple
      • e.g. Student(t) means that t is a tuple in the Student relation
    • Extension is the set of all instantiations for which the predicate holds true
    • An extension is equivalent to a relation

  • Safety

    • It is possible to write relational calculus queries that describe infinite results
      • e.g. \{t | \neg Student(t)\} describes all tuples aren’t in the Student relation, which could be infinite
      • These queries are described as unsafe
    • It is important that RC queries are safe / range-restricted

7. Physical Database Design

7.1 Physical Storage and File Structures

Disk/Page Model

  • Databases are too large to fit in main memory, so they are stored on disk

  • Disk I/O is expensive, so DBs move data in fixed-sized blocks called pages, which are stored on disk as disk-blocks

    • DB reads/writes whole pages, not individual rows
    • a table is stored as a collection of disk blocks

  • Storing records on disk can be done in two ways:

    • Unspanned organisation - records don’t span across disk blocks
      • this can cause internal fragmentation
    • Spanned organisation - records can cross boundaries
      • this requires pointers to link record fragments

  • The blocking factor is the number of records stored in blocks

  • File block - filesystem-level chunk for files

    • The ith disk block refers to the block on disk allocated to contain the contents of the ith file block

  • The query cost is defined in terms of the number of disk block accesses needed

Organising DB data on disk

  • Used for DB to keep track of which pages belong to the file/table
Contiguous Allocation
  • A file/table occupies a contiguous run of blocks on disk
  • Pros:
    • Very fast sequential scans
  • Cons:
    • Hard to grow: if you need more space, you may have to move the file
    • Fragmentation issues in long-running systems
Linked Allocation
  • Each block contains a pointer to the next block (a linked list of blocks)
  • Pros:
    • Easy to grow
    • No need for contiguous free space)
  • Cons:
    • Sequential access
    • Pointer overhead and poor locality
Indexed Allocation

  • Maintain an index structure that tells you where the blocks are

    • Either a table with a header pointing to all its pages
    • Or a multi-level index like B-trees

  • This is the most common real-world implementation

  • Pros:

    • Good random access
    • Still easy to grow

  • Cons

    • Extra metadata to contain

Structuring DB data on disk

  • About file organisation for a table: how records are placed into pages
Heap Files

  • Records are stored wherever there’s space; no particular order

  • Operations:

    • Insert: fast (add to the end)
    • Lookup by key:
      • without an index: must scan
      • with an index: index gives you the page + slot
    • Range Query: without index: scan

  • Heap files are good when:

    • require lots of inserts / updates (e.g. online transaction processing)
    • rely on indexes for fast queries
Sequential (ordered) files

  • Records are stored sorted by some search key

  • Operations:

    • Lookup: use binary search
    • Range queries: fast
    • Insert: expensive (worst case: move half the pages)
    • Updates that change the key: costly

  • Sequential files are good when:

    • Workloads dominated by range scans on that ordering key
    • Time-series data if stored/clustered by timestamp
Hash Files

  • Use a hash function on a key to choose a bucket/page

    • Records with the same bucket go in the same page chain/bucket structure

  • Operations:

    • Equality lookup: very fast on average
    • Range queries: bad
    • Complicated to handle growth

  • Overflow buckets may be needed to store records inserted into full buckets

  • Hash files are good when:

    • Heavy equality lookups, few range queries

7.2 Indexes and query performance

Introduction to Indexes

  • An index is an extra data structure that maps search key -> row location

    • which helps the DB avoid scanning the whole table

  • In PostgreSQL and MySQL, defining a PRIMARY KEY or UNIQUE constraint automatically creates a unique B-Tree index to enforce it.

  • In MySQL, foreign keys (child table) get an index created automatically

    • PostgreSQL does not do this

  • Separate indexes can be created using the CREATE INDEX statement:

    • e.g. CREATE INDEX idx_orders_user_id orders(user_id);

  • Pros

    • Fast filtering (WHERE clause)
    • Fast joins (especially joining on PK/FK)
    • Fast ordering + LIMIT

  • Cons

    • More storage
    • Slower writes (must maintain indexes)

Types of Indexes

B+ Trees
  • A B+ tree is the most common index structure.
  • It is a balanced search tree that stores keys and child pointers in internal nodes, and key entries at the leaf nodes
    • All leaves are at the same depth
  • It is space efficient - fits into a disk page
  • Finding row locations in the B+ tree is logarithmic time, which is very efficient
    • suitable for range queries and equality queries
Hash Indexes

  • Hash index helps equality lookups but not range queries

    • uses a hash function on the search key to find the bucket containing matching entries

  • Not suitable for range queries or ORDER BY, so it is less widely used

Clustered Index

  • A clustered index is where the table’s rows are stored physically in the same order as the index key

    • the “table” is the clustered index

  • Pros:

    • range queries on clustered key
    • ORDER BY clustered key

  • Cons:

    • inserting into middle can cause page splits/fragmentation
    • updating clustered key is expensive
    • only one clustered index

  • For example, in MySQL the PRIMARY KEY is clustered

Non-Clustered Index

  • A non-clustered index is where the index is a separate structure

    • leaves contain key -> row locator, not the row data stored in that order

  • Pros:

    • speeding up lookups on non-clustered columns
    • multiple indexes on different columns

  • Cons:

    • DB may need extra reads to fetch the actual table rows
    • range scans may involve many random reads if rows are scattered
Covering Indexes
  • A covering index is an index that contains all the columns needed to answer a query
  • Allows DB to skip reading the table at all
  • Also known as index-only access in PostgreSQL

Query Planning & Performance

Introduction

  • A query plan is the DBMS’s steps for executing the planned SQL query

  • Query optimisation is the process of choosing the best plan for that SQL query

  • Decisions that might be made are:

    • Using what join algorithm
    • Whether sorting, aggregation, hash tables are required
    • What order to perform these steps

  • Internally, relational algebra is used for query optimisation.

Query Planning

  • Internally, the DBMS performs these steps:

    1. Parse
      • check syntax, resolve table/column names, types, functions
    2. Rewrite
      • Expand views, simplify predicates
    3. Plan/Optimise
      • Picking joining algorithms, indexing, table sizes etc. to estimate costs
    4. Execute
      • Execute the query plan

  • A query plan is a tree of operators like:

    • Seq Scan - scan the whole table
    • Index Scan / Index Only Scan
    • Bitmap Index Scan + Bitmap Heap Scan
    • Sort
    • Aggregate
    • Joining algorithms - NestedLoop, Hash Join, Merge Join

  • The DBMS uses statistics to estimate costs, to pick the best query plan to execute

EXPLAIN
  • The EXPLAIN statement can be used to show the planned query pln
  • EXPLAIN (ANALYZE) runs the query and shows real timings and row counts

8. Database System Design

8.1 Transactions and ACID

  • A transaction is a sequence of reads/writes treated as one logical unit

    • it either all happens (commit) or none happens (rollback)

  • For example: bank transfer transaction occurs as one atomic operation

    1. subtract from A
    2. add to B

  • The ACID principles of relational databases describe the properties of transactions

    • A - Atomicity
      • All or nothing. If the transaction fails halfway, DB undoes partial changes
    • C - Consistency
      • DB moves from one valid state to another
      • Valid is defined by constraints/triggers
    • I - Isolation
      • Concurrent transactions don’t interfere in ways that break correctness
      • Result is equivalent to serial execution
    • D - Durability
      • Once committed, changes survive crashes/power loss

8.2 Concurrency control, Locking, Deadlocks

Concurrency Control

  • Concurrency control is a mechanism that allows simultaneous execution of transactions while maintaining ACID principles.

  • If concurrency isn’t controlled, you can get:

    • Lost update: one overwrites the other
    • Dirty read: read data another transaction hasn’t committed yet
    • Non-repeatable read: read row twice and changes in between
    • Phantom read: range query is rerun and rows appear/disappear

  • Isolation levels decide which of these are allowed

Locking

  • Transactions must acquire locks before accessing data:

    • S (shared) lock for reading
    • X (exclusive) lock for writing

  • Two-Phase Locking (2PL) enforces a rule:

    1. Growing phase: transaction acquires locks, does not release any
    2. Shrinking phase: transaction releases locks, cannot acquire new ones

  • This enforces the schedule is conflict-serialisable (equivalent to some serial order)

  • Disadvantages:

    • Blocking: transactions wait for locks
    • Deadlocks: cycles of waiting occur; DB detects and aborts one victim
Timestamps

  • Give every transaction a timestamp when it starts, enforces all conflicting operations occur in timestamp order

  • Basic-timestamp ordering is a protocol that uses timestamps.

    • abort if reading/writing is invalid

  • Pros:

    • No deadlocks
    • Good for high contention

  • Cons

    • Can cause lots of aborts/restarts
    • Starvation possible

  • MVCC (multi-version concurrency protocol) builds upon timestamps and is a widely used protocol for concurrency control

Isolation Levels

  • Isolation level is the contractfor how much interference between concurrent transactions is allowed

  • Common isolation levels are:

    • READ UNCOMITTED
      • dirty reads allowed
    • READ COMITTTED
      • no dirty reads
      • Non-repeatable reads and phantoms can happen
    • REPEATABLE READ
      • no dirty reads or Non-repeatable reads
      • phantoms can be possible
    • SERIALIZABLE (strongest)
      • prevents all anomalies

8.3. Recovery and Durability

Motivations for Recovery

  • Durability means: once a transaction commits, its effects must survive power crashses (power loss, OS crash, DB restart)

  • Recovery is the DBMS process after the crash to ensure Atomicity and Durability:

    1. All committed transactions are reflected in the database (durability)
    2. No uncommitted transaction leaves partial changes behind (atomicity)

Log-based Recovery

  • Log-based recovery (Write Ahead Logging) is the standard approach in most DBs

  • Mechanism:

    • Updates happen in memory -> pages become dirty
    • Before a dirty page is written to disk, DB appends a log record describing the update and forces the log to disk first

  • This provides durability as the commit is logged on disk. This allows:

    • REDO committed updates that weren’t written to data pages yet
      • ensures durability
    • UNDO incomplete (uncommitted) updates
      • ensures atomicity

  • A transaction is durable when its commit record are flushed to disk

Shadow Paging

  • Shadow paging keeps a shadow page table that points to the stable version of each page

  • When a transaction updates a page

    • original page is not overwritten
    • write modified page to a new location
    • update currentp age table to point to the new page

  • On commit, you atomically switch from the shadow page table to the new page table

  • This is crash-safe as:

    • If crash before commit: shadow table is used; changes are ignored
    • If crashes after commit: root pointer points to new pages; changes are preserved

  • Disadvantages:

    • Fragmentation - pages get written to new locations constantly
    • Expensive for many updates
    • Hard with concurrency
    • Not great for long-running transactions

Checkpointing

  • Checkpointing is an optimisation to WAL that reduce recovery time

    • With normal WAL, scanning the log from the beginning takes a lot of time

  • Periodicially, the system performs a checkpoint operation, which:

    1. forces all log records from memory to disk
    2. forces all modified database pages from memory to disk
    3. writes a checkpoint record into the log file

  • When recovery is needed, the DBMS finds the last checkpoint

    • prevents the DBMS from starting from the beginning

Backups

  • Backups are the last safeguard against severe failures such as a complete disk crash
  • Types of backups:
    • Full backup - complete copy
    • Differential backup - copy of only data that has changed
    • Point-in-time recovery (PITR) - restore a base backup + replay logs up to a timestamp

8.4 Security and Access Control

Introduction

  • Database security is the set of policies and mechanisms that protect a database’s confidentiality, integrity, and availability

  • The main control measures are:

    1. Access control
    2. Inference control
    3. Application-level defences
    4. Flow control
    5. Data encryption

  • The database administrator (DBA) is a central authority for database security

    • holds a powerful superuser account
    • performs tasks like creating accounts, granting/revoking privileges, assigning security levels/roles, and defining/enforcing security policies

  • A DB system log requires all update operations

    • A database audit is reviewing the log to trace suspicious actions

  • Security: protect all sensitive data

  • Precision: reveal as much nonsensitive data as possible

  • Privacy: appropriate use of personal information

  • Tradeoff: perfect security often reduces precision

Access Control

  • Access control (authorisation) is ensuring only authorised users can read/write specific data
Discretionary Access Control (DAC)

  • Owner/admin grants privileges on DB objects

  • User privileges are applied to the account independently of specific tables

    • e.g. CREATE TABLE, ALTER, SELECT etc.

  • Object privileges are applied per table/view

    • e.g. SELECT, INSERT, UPDATE, DELETE, REFERENCES

  • GRANT and REVOKE are used to grant/revoke privileges to accounts

  • Users can grant privileges to other users:

    GRANT SELECT ON empl TO u1 WITH GRANT OPTION;

  • Some DBs extend DAC to allow for propagation limits:

    • Horizontal: define how many other users can be passed the privilege
    • Vertical: define how many times privilege can be passed successively

  • DAC is flexible but can be vulnerable to trojan horse programs

  • Pros:

    • flexible and easier to manage for many applications

  • Cons:

    • weaker against malicious software and information leakage

  • More common in SQL

Mandatory Access Control (MAC)

  • MAC is a system-wide policy based on labels/clearances

  • Data and users have labels; access is decided by comparing labels (not the object owner)

  • Security level stack:

    1. Top Secret
    2. Secret
    3. Confidential
    4. Unclassified

  • Most common model is the Bell-LaPadula Model

    • No read up - low subjects can’t learn from higher objects
    • No write down - higher subjects can’t write to lower objects

  • With MAC, views are filtered by clearance. This leaves two options:

    1. unauthorised users don’t see the tuple at all
    2. unauthorised users just see NULL
    • second option leads to indistinguishability with presence of data

  • With MAC, we require polyinstantiaion

    • Multiple tuples can share the same apparent key
    • Real key is (key, classlevel)

  • Pros:

    • very strong protection; prevents illegal information flows

  • Cons:

    • Rigid; requires strict classification and labeling

  • Only common in high-security settings

Role-Based Access Control (RBAC)

  • Permissions are assigned to roles, users are assigned roles

  • Roles are organised in a hierarchy reflecting authority

    • hierarchy is a partial order

  • Scales better than DAC-per-user, and supports least privilege

  • In SQL, RBAC is supported by granting privileges to roles, and then granting roles to users. e.g.

    GRANT SELECT ON orders TO analyst_role;
GRANT analyst_role TO alice;
Row-Level, Column-Level, Label-Based Security

  • Row-level Security enforces a per-row predicate for each user/role

    • e.g. users can only see their own rows

  • Column-level Security restricts access to certain columns, even if users can access the table

    • this is primarily done by views that expose only allowed columns

  • Label-level security is where each row has a security label and each user has a clearance

    • uses MAC-style access control
    • is a special form of row level security

Application-level Defences

  • One of the most common application-level attacks is SQL injection - when an attacker supplies input that gets treated as part of the SQL code

    • can maliciously change what the query does

  • Two main types

    • Code injection - inject code like ... OR 1=1
      • mainly used to bypass auth / dump data / modify schema & data
    • Functional-call injection - use database functions
      • e.g. time-based probing / DoS using pg_sleep / SLEEP()

  • Countermeasures

    1. Paramterised queries / prepared statements
      • send SQL + values separately, so DB never parses user input as code
    2. Least privilege for application DB user
      • restrict privileges, e.g. app account shouldn’t be able to DROP
    3. Avoid dynamic SQL
    4. Input Validation & Function Security
      • filter and validate all user input
      • restrict powerful database functions callable from SQL
    5. Safe stored procedures
    6. Monitoring/WAF/logging

Inference Control

  • Inference control is about stopping users from learning sensitive facts indirectly from allowed queries
  • Common controls are:
    • suppress results for small groups (k-threshold)
    • generalise data (age bands, regions)
    • add noise to aggregates

Flow Control

  • Flow control is about preventing information from a high-sensitivity source from leaking to a low-sensitivity sink

  • Explicit flow is when the sensitive value is directly copied into an output

  • Implicit flow is when sensitive value affects control flow, and ooutcome leaks often through public logs

  • Covert channels are a way of communicating information through a mechanism not indended for communication, e.g.

    • Storage covert channel - toggling a lock to transmit bits
    • Timing covert channel - leaking through how long something takes

9. Applications and Alternatives

9.1 Application Architecture

  • Applications are typically designed as 3-tier:

    1. Client / mobile
    2. API / service
    3. Database

  • Typically, one user action / API reuqest maps to one transaction

    • keep transactions short

  • Connection pooling is used to reuse connections across requests

    • this is because DB connections are expensive
    • limits max concurrency to avoid overwhelming DB

  • An Object-Relational Mapping (ORM) is an interface for the database instead of SQL

    • ORM: faster development, but risks issues like N+1 queries, accidental huge joins
    • SQL: maximum control and performance clarity

  • In production systems, migrations to the schema are used when modificiation is required:

    • roll forward safely
    • often do backwards-compatible steps

  • Caching

    • Use caches (e.g. Redis) for hot reads
    • Use materialised views / summary table when analytics queries are heavy

9.2 NoSQL

SQL Databases

  • A SQL database is a relational database

  • Pros of SQL Databases:

    • Strong consistency + transactions
    • Joins and powerful ad-hoc querying
    • Schema + constraints enforce invariants
    • Mature optimisers, indexes, tooling

  • This makes SQL databases good for:

    • Most online transaction payment (OLTP) business apps
    • workloads where correctness matter a lot

NoSQL Databases

  • NoSQL (non-relational databases) are a family of databases that relax some relational features to gain:

    • sacability
    • flexibility of data model
    • performance for certain access patterns

  • The main families are:

    • Key-value store: (Redis style)
      • great for caching, sessions, simple lookups
    • Document stores (JSON docs)
      • flexible schema, nested structures
      • good when data naturally fits “one aggregate per document”
    • Wide-column
      • rows with many sparse columns, designed for huge scale
      • good for time series / logs with predicatble queries
    • Graph DBs
      • nodes/edges, traversals
    • Search engines
      • inverted indexes, relevance ranking, full-text search

  • Tradeoffs vs SQL

    • Often weaker support for joins, multi-row transactions, and ad-hoc queries
    • Strong performance when access pattern matches the model
    • Usually design around query patterns first

  • When to use NoSQL

    • schema is highly variable or nested and joins are complex
    • need high horizontal scaling
    • can accept weaker consistency / transactions

9.3 Distributed Databases

  • A distributed database stores data across multiple machines to improve:

    • availability
    • fault tolerance
    • throughput / storage capacity

  • Replication is making copies of the database

    • Leader-follower replication is most common: writes go to primary, replicas serve reads
    • Consequences: replication lag - reads from replicas may be stale

  • Sharding is splitting the database into multiple parts

    • Data is divided by a shard key:
      • Hash sharding: good balance, bad for range scans
      • Range sharding: good for range scans, risk hotspots
    • Key consequences
      • queries not using shard key may hit many shards
      • cross-shard joins and transactions are much harder

  • The CAP Theorem states:

    • During a network partition, systems trade off:
      • Consistency - everyone sees the same latest value
      • Availability - every request gets a response
    • So under a network partition, you trade C for A

  • Consistency models

    • Strong consistency - reads reflect the latest committed value
    • Eventual consistency - replicas converge over time
    • Session consistency - a common middle-ground guarantee

  • Distributed transactions

    • Coordination is required if transaction is split across multiple shards
    • 2PC (two-phase-commit) can be used but doesn’t solve the full problem
    • Cross-shard transactions are just avoided in general
